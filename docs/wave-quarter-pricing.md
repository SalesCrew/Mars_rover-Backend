# Quarterly wave pricing

Display, cartonware and individual wave articles are selected from `quarter_price_catalog`. The server resolves the current Europe/Vienna quarter at booking time and stores the article, quarter, order quantity, VE size, order price and immutable catalog source on the submission. Individual quantities remain pieces internally; the UI accepts whole VEs. Percentage targets do not control whether prices are stored or exported.

Catalog imports require an admin and record the workbook filename, SHA-256 and exact source cells. Prices for a quarter are immutable: a conflicting price or VE size rejects the whole import. Imports and historical reconciliation RPCs are restricted to service_role, behind authenticated admin API routes. The public tables have RLS and no client-role access.

Legacy bookings remain usable. Installing the migration changes no existing booking prices. Exports prefer booking snapshots and label unconfirmed legacy prices. The single-wave export always includes revenue and a Buchungsdetails worksheet with article numbers, ordering units, prices and source quarter.

Historical reconciliation is separate: GET `/api/wellen/catalog/reconciliation` produces a read-only preview and confirmation token; POST with that token applies only uniquely proven article/quarter matches, in one audited transaction. Existing snapshots retain their original article identity. For legacy master-product or wave article references, both article number and full normalized name must match. Missing evidence remains unchanged and appears in the downloadable report. A stale preview rejects the operation. Quantities, dates, ownership and original IDs are preserved. Audit rows retain all old pricing metadata.

The follow-up migration `20261112152854_wave_catalog_validity_and_exact_legacy_matches.sql` records the supplier document start date and business approval separately from the applied quarter. A source dated differently from the quarter start requires a recorded approval note. Historical lines without any saved article number may use a unique full normalized name and the same article type in that quarter; ambiguous names and conflicting saved article numbers remain unresolved. A stored normalized-name column and index avoid repeatedly normalizing the catalog for each legacy booking. Matching method is retained in the reconciliation audit.

The XLSX parser resolves parent article and full price columns from headers, including older Pet layouts. Missing source prices are reported and excluded, preserving real zero prices. The original workbooks remain unchanged. Explicit quarterly source approvals are business evidence; supplier document dates are retained rather than rewritten.

Verification uses generated synthetic XLSX files and in-memory PGlite. Backend: `node --import tsx --test tests/*.test.mjs` and `npm run build`. Frontend browser runner: `node --import ./backend/node_modules/tsx/dist/loader.mjs tests/quarter-pricing-browser.mjs`; it expects an isolated backend checkout at `frontend/backend`, Playwright on NODE_PATH, and no .env files. It refuses external fetches and exercises UI import, percentage-wave creation, whole-VE ordering, authorization failures, atomic validation, retry idempotency, article-ID retention and actual Excel generation. Frontend unit tests use the same loader with `--test tests/*.test.mjs`.

Application rollback can redeploy the previous backend/frontend commits while retaining additive schema and evidence. Never drop catalog/audit tables or guess older quarter prices. A reviewed data rollback must restore only the saved audit before-images within a transaction and account for the snapshot update guard; do not reverse quantities or delete bookings.

For separately reviewed, customer-specific legacy identities, `scripts/legacy-wave-mapping.mjs` generates a read-only SQL preview and a token-guarded data operation. It has no database connection or credential handling. A plan must identify each exact Billa Plus wave/article UUID, original labels, original booking count, six-digit SKU and mapping-workbook SHA/sheet/row. Only display and cartonware lines are supported. Do not infer an identity from approximate names or silently repair a contradictory source SKU.

Individual-product entry is always in VEs in the GL order dialog, GL history add/edit and admin entry/edit. The piece/VE toggle was removed. Internal quantities remain pieces; order metadata and labels preserve the VE count. Missing or ambiguous VE sizes are shown and blocked; pallet capacity is not a VE fallback.

Migration `20261113091431_wave_single_products_always_ve.sql` adds service-only, invoker helpers for explicit wave/product VE resolution and extends the existing insert/update guards. It changes no existing rows. Legacy inserts now require whole VEs and store VE/order metadata with an authoritative server-side legacy unit price. These prices remain explicitly unconfirmed if no quarterly source exists. Catalog-linked entries retain the existing immutable-quarter behavior. Quantity edits keep stored VE metadata consistent; existing historical piece snapshots remain readable.

`scripts/correct-confirmed-ve-orders.mjs` generates a separate, admin-only reviewed operation for business-confirmed historical unit mistakes. It requires exact booking IDs and batches, one-VE sizes, price/source evidence, the business approval and a fresh snapshot token. It corrects only the listed rows, preserves all other fields, records full before/after images and approval in the existing audit table, and is idempotent. It must never be used to reinterpret arbitrary historical quantities of one.

Verification: `node --test tests/waveVeOrders.test.mjs` (generated data only); frontend helper tests; `tests/ve-orders-browser.mjs` exercises actual GL, master-product, admin, history, cached-client rejection and Excel-export paths through the real local API and PGlite. No source workbooks or production rows are test fixtures.


The operation requires an existing admin actor, locks the selected bookings/definitions, referenced parent waves and catalog rows, and rejects stale snapshots, missing quarter prices, conflicting saved/frozen identities or changed labels/counts. Parent locks block new booking foreign-key references during application. It changes only the reviewed definitions' article number/catalog key and the selected bookings' price metadata; it retains the old definition price, names/date labels, targets, quantities, dates, markets and ownership. A single audit insert records full booking and definition before-images, exact catalog evidence and the mapping source. Validation/audit errors roll back the whole transaction. A second preview/apply is a no-op. No schema change or runtime deployment is needed.

Before application, independently compare the mapping source and approved catalogs, review the actual read-only preview, then run `node --test tests/legacyWaveMapping.test.mjs` and the existing quarter-pricing checks. These tests use only generated synthetic data in PGlite, including more than one REST page, quarter boundaries, same-name competing articles, out-of-scope rows, SQL quoting, stale plans, existing frozen prices and audit-failure rollback. Never pass production mappings or supplier workbooks into the test database. Archive the reviewed plan, token, exact SQL and verification evidence outside the repository; use a fresh preview token immediately before the authorized production operation. A rollback is a separate reviewed maintenance action using the audit before-images and the existing frozen-price guard.
